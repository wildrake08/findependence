UX-003 · Interface craft assessment · v0.6.0-alpha candidate (94dd389) · 27 September 2026

Findependence Interface Craft Review

UX-001 and UX-002 asked whether a household member can reach each outcome. This review asks a narrower question: is the interface's visual and interactive execution resolved at every level a person can perceive? That covers type, spacing, control geometry, colour, states, focus, tables, phone layout, and behaviour over time. It recommends the smallest set of changes that would close the gaps, and says which of them belong in the stylesheet as rules rather than as fixes to single pages.

Prepared by ACT-002, the same agent that built these versions, so read it with that bias in mind. It is a proposal, not a canonical change: it alters no Requirement or ratified artifact. Every figure comes from the demo family, whose names, figures, and relationships are invented.

1 Craftsmanship diagnosis

The current language

The interface is a single server-rendered stylesheet of about 75 rules (web.ex @css, lines 1024–1101), with no JavaScript, no web fonts, no images, and no motion. Every page is a column of white bordered cards (radius 10 px) on a pale grey ground, set in the platform's system-ui face at 16 px / 1.5. The palette has eight named tokens (ink, muted, line, bg, card, accent #1f5fbf, ok, err) plus about ten literal colours. Data is shown in plain tables that restyle into stacked grids below 40 rem. The tone is plain and utilitarian, which suits a private, local research prototype whose rule is that nothing is scored or suggested.

Strengths to preserve

  • Restraint. No decoration, gradients, shadows, or animation, and no visual element that implies a judgment. Cards are the only surface treatment, and each one maps to a section heading.
  • Money is set with care. Tabular figures in every numeric cell, a true minus sign (U+2212) that never separates from its amount, and explicit + for money in.
  • The phone tables are designed, not squeezed. Four purpose-built grids (compact, dist, flow, and the default) keep table semantics through explicit roles (UX-001 R10).
  • Correctness of structure. Every control has a label; field errors are linked with aria-describedby; checkbox labels wrap their inputs, so the label is the hit area; axe-core finds nothing on 53 page types.
  • Performance. Pages are complete on first paint: inline CSS, no font loading, no assets that arrive late, and therefore no layout shift. Server time is under 22 ms at 200 items (UX-002 E3).

Most significant craft deficiencies

  1. The keyboard focus ring is too faint for its job (K1). The amber outline #f0b400 measures 1.87:1 against the white cards and 1.74:1 against the page ground. It also uses the same hue as the “Waiting for you” attention border, so focus and “needs you” share one colour signal.
  2. Numeric columns don't hold their alignment (K2, K3). All nine data tables right-align their figures under left-aligned headers. The “Below zero” pill sits inside the number's cell and pushes each negative balance 92 px left of the positive balances above and below it. These are the rows the cash-flow views exist to show.
  3. Form controls have four heights (K4): inputs 38.8 px, selects 35.8 px, date fields 40.8 px, compact buttons 30 px. Because rows align controls by their bottom edges, labels over selects sit 3 px lower than labels over inputs. Selects also keep the browser's grey fill, which reads as disabled next to white inputs.
  4. Links have no rule of their own (K5). They use the browser's default blue #0000ee, a second blue beside the accent, and turn purple once visited. So “Plans” or “Retirement” changes colour depending on history, not on anything in the household.

Systemic cause

Most defects come from missing system rules, not from design decisions or careless execution. The stylesheet defines colours but not roles for focus, links, control height, button hierarchy, numeric headers, or card rhythm. Each page therefore inherits browser defaults where a rule is absent. The fixes are almost all single rules in @css plus one helper change in html.ex. One (K10, amount and frequency in one cell) is a component decision.

2 Findings

Impact is perceptual impact. Each finding is traced from evidence to verification. “Rec” points to the implementation entry in section 6.

Craft defects

K1 · Focus ring below non-text contrast, and sharing a hue with “attention” High pervasive · system-wide · small · easy · confidence high

Surface
Every focusable control on every page.
Observed evidence
E1: :focus-visible{outline:3px solid #f0b400;outline-offset:2px}, repeated for date inputs. E4: 1.87:1 against --card (#fff), 1.74:1 against --bg. E2: on Dad's home page, the focused “Agree” button sits inside the “Waiting for you” card, whose border is #c79a1e. Ring and border are both amber, a few pixels apart.
Craft issue
The ring is visible because it is thick and saturated, but it falls below the 3:1 that WCAG 1.4.11 asks of the visual information that identifies a state. The amber hue also already means “needs your attention” (badge and attention card), so a focused control inside that card is harder to pick out.
Principle
Accessibility integrity; state differentiation; one meaning per colour.
Root cause
No focus token: a literal chosen for salience on white, without a contrast check. The Tab walk (WI-024, WI-041) confirms that an outline exists, not that it can be seen.
Recommendation
C1. A --focus token that clears 3:1 against every surface it can sit on and doesn't reuse a semantic hue.
Acceptance
The focus indicator has at least 3:1 against --card, --bg, and the .msg tints; it differs in hue from the attention, error, and accent colours; it is at least 2 px thick on every control type, including date inputs and summary.
Verification
Extend tabwalk.py to read each focused element's computed outline-color and compute its contrast against the nearest opaque ancestor background, failing below 3:1. Human check: Tab through home, and pick out focus at arm's length.

K2 · Numeric column headers left-aligned over right-aligned figures Moderate pervasive (9 tables) · component · small · easy · confidence high

Surface
Coming up, next 60 days, next 12 months, debts, plan month-by-month, retirement year-by-year, “What changes the result”, totals by value, balances.
Observed evidence
E1: every header is built as <th role=columnheader scope=col> with no class (html.ex lines 188, 334, 371, 482, 757, 859, 1365, 1554, 2167); only td gets .num. E3: the “Net” header spans 687–714 px; the figures under it end at ~795 px. E2: on the next 12 months, “In”, “Out”, and “Net” each sit over the gap left of their column.
Craft issue
The header doesn't sit over the thing it labels. In a five-column table of similar figures, the eye pairs “Out” with the end of the “In” figures.
Principle
Alignment; visual grouping; typography of tabular data.
Root cause
The table helpers take header labels as plain strings, with no alignment attribute.
Recommendation
C2. Mark numeric headers and give th.num right alignment.
Acceptance
In every table, the right edge of each numeric header's text lies within 1 px of the right edge of its column's figures (1200 px).
Verification
A unit test that every th in a column whose tds carry num also carries num, across the captured pages; one screenshot review of the next 12 months.

K3 · “Below zero” pill breaks the balance column Moderate repeated · component · small · easy · confidence high

Surface
Coming up (home) and the next 60 days: the “Balance after” column (html.ex lines 310, 1348).
Observed evidence
E3: positive balances end at 995.5 px; below-zero balances end at 903.6 px, because the pill follows the amount inside the right-aligned cell. E2: Dad's next 60 days has nine below-zero days, so the column zigzags down the page. At 390 px the pill wraps to its own line at a different x position in each row (138 px, 124 px).
Craft issue
The rows that matter most lose the column alignment that lets a reader compare balances by scanning down. The zigzag also reads as a layout glitch rather than a signal.
Principle
Alignment; perceptual precision; state treatment that doesn't disturb structure.
Root cause
The state marker is inline text placed after the value in a right-aligned cell.
Recommendation
C3. Put the pill before the amount, so the amount stays flush right; on phones, give it a fixed position in the grid.
Acceptance
In both tables, every balance's right edge is within 1 px of the others (1200 px). At 390 px, every pill starts at the same x within a table.
Verification
Geometry script over the next 60 days (the same measurement as E3); visual-regression snapshot of the next 60 days at both widths.

K4 · Four control heights; stair-stepped labels; grey selects Moderate pervasive · system-wide · small · easy · confidence high

Surface
Every form row: add item, add value, add account/debt, plan steps, share/link/account selects on item pages, unlock.
Observed evidence
E3: input 38.8 px, select 35.8 px, date 40.8 px, button 38.8 px, compact buttons and a.button-link 30 px. form.row uses align-items:flex-end, so on “Add an account” the “Kind” label sits 3 px below “Name”. On the plan's “Add planned money” row, “How often?” drops below “Planned item” and “Amount”. E4: select fill is the browser's #efefef, 1.15:1 against the white inputs beside it. On unlock, the “Who are you?” select looks inert next to the passphrase field.
Craft issue
Controls in one row don't share top edges or baselines, so rows read as uneven. The grey select looks disabled.
Principle
Component refinement; design-system coherence; state clarity (enabled vs disabled).
Root cause
Height comes from padding plus each control's intrinsic metrics, not from a shared token; select has no background rule.
Recommendation
C4. A --control-h token applied as min-height to input, select, and button; an explicit select background and border matching inputs.
Acceptance
Within any form.row, all text inputs, selects, date inputs, and submit buttons have equal rendered height (±0.5 px) and equal top edges. No enabled control has a fill that differs from --card.
Verification
Geometry script on add item, add account, and plan pages; visual check in Firefox and Safari (select rendering differs by engine).

K5 · Links use browser defaults, including visited purple Moderate pervasive · system-wide · small · easy · confidence high

Surface
Every link: item names, “← Everything”, the feature links in Coming up, the leaving links, “No, go back”.
Observed evidence
E1: the stylesheet has no a rule except a.button-link and the header. E2: links render #0000ee; the accent (buttons, summary “Month by month”) is #1f5fbf. On the plan page, the blue of the “Month by month” disclosure is visibly different from the blue of “← Plans”. Visited links become #551a8b.
Craft issue
Two unrelated blues for interactive text, and a colour state (visited) that carries no meaning in an app whose pages are all visited routinely.
Principle
Palette coherence; semantic colour use; restraint.
Root cause
Missing link rule.
Recommendation
C5. A link rule using --accent for both unvisited and visited, with a set underline offset.
Acceptance
Every link and summary computes to --accent, before and after visiting; links remain underlined (not colour-only, WCAG 1.4.1).
Verification
Computed-style check over the captured pages; the accent on white is 6.09:1, so contrast is unchanged in kind.

K6 · Field errors placed after the whole row, away from the field Moderate repeated (7 forms) · component · small · easy · confidence high

Surface
Add item, plan steps, balances, retirement assumptions (.field-error, 7 uses).
Observed evidence
E2, add item with amount “55,5” at 1200 px: the Amount field has a 1 px red border; the message “Enter an amount like 62.40 or 1,200.” appears at the far left, below the date, radios, and Add button, about 90 px below and 230 px left of the field it refers to. At 390 px it appears below the Add button.
Craft issue
The field and its message aren't grouped by proximity, and the only mark at the field is a 1 px colour change. The link exists for screen readers (aria-describedby) but not for sight.
Principle
Grouping; state completeness (error); proximity.
Root cause
.field-error is a full-width flex item appended to the form, not a child of the field's p.
Recommendation
C6. Render the message inside the invalid field's wrapper, directly below the control, and strengthen the invalid border to 2 px without shifting layout.
Acceptance
At both widths, the message's top edge is within 0.5 rem of the invalid control's bottom edge and shares its left edge. The invalid control's border is 2 px (visual) with no change to control height. aria-describedby still resolves.
Verification
The existing field-error tests plus a geometry assertion; screenshot of add item with an invalid amount.

K7 · Destructive “Delete plan” styled as a neutral action Low–moderate isolated · local · small · easy · confidence high

Surface
Plan page, “Delete this plan” card.
Observed evidence
E1: html.ex line 620 uses the neutral button/5 helper (accent outline). Item “Delete…”, “Leave the household”, and the confirm buttons use .danger (red).
Craft issue
The same kind of action (removing something the member made) has two visual treatments, and one of them looks identical to “Remove” for a plan step.
Principle
Semantic state consistency; cross-interface coherence.
Root cause
The helper has no variant parameter.
Recommendation
C7. A variant argument on button/5; danger for delete-plan. Whether deleting a plan should also ask for confirmation is a UX-001 R3 question; this review does not decide it.
Acceptance
Every control whose action deletes, relinquishes, or leaves carries .danger.
Verification
A markup test listing destructive actions and asserting the class.

Systemic refinements

K8 · Card bottom spacing varies; lists end with an orphan rule Low–moderate pervasive · system-wide · small · easy · confidence high

Surface
Every card; most visibly Waiting for you, Waiting for others, and Leaving.
Observed evidence
E2: cards have 16 px top padding (h2 margin .25 rem), but the last child's own bottom margin (1 em for p, ul) adds to the 16 px padding, so bottom space varies between about 24 and 34 px. ul.plain li draws a bottom border on the last item too, so “Waiting for you” ends with a rule, then empty space, then the card edge.
Craft issue
Cards look bottom-heavy by different amounts, and the trailing rule reads as a missing next row.
Principle
Spatial rhythm; restraint (redundant dividers).
Root cause
No first-/last-child margin reset inside cards.
Recommendation
C8. Trim first and last child margins inside .card; no border on a plain list's last item.
Acceptance
For every card on the captured pages, the space from the last content box to the card's inner edge equals the top padding (±1 px); no ul.plain shows a border on its last item.
Verification
Geometry script over the captured pages; visual-regression snapshots.

K9 · Header not on the content column; phone header clusters Low–moderate pervasive · system-wide · small · easy · confidence high

Surface
Page header on every page.
Observed evidence
E3: at 1200 px the wordmark starts at x = 16 px and “Lock” ends at 1180 px, while cards run from 160 px to 1032 px. E2: at 390 px, the “1 waiting for you” badge wraps above “Dad” and “Lock”, starting at a different x from the name beneath it.
Craft issue
At desktop widths the header and body use two different frames, so the product name floats far left of everything it heads. On phones, the three header items form an unaligned cluster.
Principle
Grid and alignment; responsive composition.
Root cause
header is full-bleed flex with fixed 1 rem padding; main is centred at 56 rem. The header form is inline, so its children wrap as text.
Recommendation
C9. Pad the header to the same column as main; lay out its right side as a wrapping flex row, aligned to the end.
Acceptance
At 1200 px, the wordmark's left edge equals the cards' left edge and “Lock”'s right edge equals the cards' right edge (±1 px). At 390 px, the badge, name, and Lock share a right edge, or a single row.
Verification
Screenshots at 1200, 900, 390, and 320 px.

K10 · Numeric presentation: false precision, mixed cell content Low–moderate repeated · component · small–medium · easy · confidence high

Surface
Retirement; home “Your items”.
Observed evidence
E2: retirement shows “about $244,200.00”, and the page says estimates are “rounded to the nearest $100”. about/1 rounds, then formats with cents (html.ex line 828). The same applies to all five rows of “What changes the result”. On home, each amount cell holds the figure and its frequency (“−$6,800.00 twice a year”, “−$100.00 a month”), right-aligned, so the decimal points don't line up and tabular figures do nothing. One cell reads “−$2,400.00, a year, irregular”, with a comma that the others don't have.
Craft issue
“.00” on a figure the page itself calls rounded suggests precision that isn't there. On home, amounts can't be compared by scanning.
Principle
Numeric typography; honesty of precision.
Root cause
One money formatter for exact and estimated figures; amount and frequency joined into one string.
Recommendation
C10. Whole-dollar formatting for about figures. On home at desktop width, the frequency as a separate muted span in its own column (the phone grid can keep them together). Fix the irregular string.
Acceptance
No “about” figure shows cents. On home at 1200 px, every amount's decimal point lies on one vertical line (±1 px).
Verification
Formatter unit test; geometry check of the amount column.

K11 · One heading size for page titles and section titles Low pervasive · system-wide · small · easy · confidence medium

Surface
Item, plan, retirement, next 60 days, next 12 months.
Observed evidence
E2: the item's name (“Dad's paycheck”) is a 1.15 rem h2, the same as the “What it's for”, “Which account does it go through?”, and “History” cards below it. The stylesheet uses seven font sizes (1.4, 1.25, 1.15, 1, .9, .85, .8 rem), none named. .amount-big is 1.4 rem at regular weight, so the figure is larger than the name it belongs to.
Craft issue
Nothing on a detail page says “this is the page, and these are its parts”. The eye lands on the amount before the name.
Principle
Visual hierarchy; typographic scale.
Root cause
No page-title role; font sizes chosen per rule.
Recommendation
C11. A named type scale with a page-title step. Whether the page title also becomes the page's h1 (the wordmark is h1 today) is a semantic change that needs a screen-reader check.
Acceptance
Every font size in @css is a scale token. On detail pages, the page title is one step above section headings.
Verification
Token audit of @css (grep for literal rem font sizes); screenshot review of the item page.

Experiments

X1 · Larger compact buttons on touch screens experiment · confidence medium

“Agree”, “Withdraw”, “Remove”, “Lock”, and the button-links are 30 px tall. That meets WCAG 2.5.8 (24 px) but falls below the 44 pt / 48 dp that iOS and Android guidance give for touch. Raising them to 44 px under (pointer: coarse) would add height to phone pages, which UX-002 found already near their budget. Try it on Dad's home and plan pages and measure the height cost before adopting it.

X2 · Return to the card that was acted on experiment · confidence low

Every action redirects to a path with no fragment (return_to/3), so submitting in a card far down an item page reloads at the top, and the result message appears there. UX-002 counted “a refused save says so where the page opens” as a strength, so moving the message trades one clarity for another. Test with walkthrough participants: redirect to #card-id with the message rendered in that card, against the current behaviour.

X3 · One solid button per card experiment · confidence low

The plan page's “Add a step” card has three solid primary buttons (“Add switching off”, “Add planned item”, “Add borrowing”), each correct for its own form, but together they compete. An outline style for sub-form submits inside a multi-form card may make the card easier to scan. There's no basis yet for calling the current treatment a defect.

Subjective alternatives

  • Dark appearance. The page declares no color-scheme and has no dark palette, so it stays light on a dark system. That is consistent, not broken. A dark palette is a legitimate option with no evidence that users want it.
  • A brand typeface. system-ui costs nothing to load and matches each platform. A web font would add identity at the cost of load time and a privacy-relevant network request, which conflicts with the local-only posture unless it is self-hosted.
  • Bold item names in tables. Item and balance tables bold their first-column links; Coming up doesn't. Both are defensible (row title vs inline reference).

4 Motion and interaction review

Motion

There is no motion: no transition, animation, or scripted movement, and the CSP forbids JavaScript. State changes happen by full page load after a POST/redirect, and the result is stated in words at the top of the page. details disclosures open instantly.

For this product that is the right motion language, not a gap. Every change is a deliberate, recorded act on shared household records. The page that follows states what happened. Animation would add no causal information the words don't already give. Reduced-motion handling is satisfied by default.

Recommended rule: no transitions or animations. Feedback is carried by page content (result messages, “Below zero”, “waiting” counts), never by movement. If a transition is ever proposed, it must name the state change it explains and honour prefers-reduced-motion. Adding a comment to @css is enough to record this.

Interaction

  • Feedback is immediate and proportionate: a 303 redirect and a page under 22 ms of server time, with a result message. There is no pressed state beyond the browser's, which is adequate given that response time.
  • Hit areas: checkbox and radio labels wrap their inputs, so the whole label is clickable. Compact buttons are 30 px (X1).
  • Focus: order follows the DOM with no positive tabindex (WI-024), but its visibility is weak (K1).
  • Continuity after acting: the page reloads at the top (X2).
  • Micro-interactions: Agree, Withdraw, Share, and Remove each lead to a page that says what changed. Validation keeps what was typed and marks the field; its placement is the weak point (K6).

5 Visual refinement review

Hierarchy and composition. The card stack gives each section a clear boundary and order, and “Waiting for you” comes first with an attention border. The weak point is detail pages, where the title, the amount, and section headings compete (K11).

Alignment and rhythm. Most of the perceptible imprecision lives here. Numeric headers (K2), the below-zero column (K3), control tops (K4), header vs content column (K9), and card bottoms (K8) all miss by amounts from 3 px to 144 px.

Typography. Readable body (16 px / 1.5), muted secondary text at 5.6–6:1, and tabular money. The explanatory paragraphs above tables run to about 100 characters per line at 1200 px (for example, Coming up's 5-line note), which is long for dense text. Capping hint paragraphs at about 70 ch would help. This is a small, subjective-adjacent polish, so it is not listed as a defect.

Colour. Semantic colours are used for their meanings (red error and destructive, green success, blue info, amber attention), with one collision (K1) and one stray blue (K5).

Surfaces. Each border has a purpose. The fieldset border inside a card is a second nested box; it groups checkboxes legitimately, so it is kept.

Iconography and imagery. None, except the text arrow “←” and the ellipsis on actions that lead to a confirmation. Nothing needs adding.

Smallest changes with the largest perceived effect: C2 + C3 (tables line up), C4 (form rows line up), C5 (one blue), C1 (focus you can see). All are CSS or a one-argument helper change.

6 Implementation recommendations

All CSS changes go in @css in web.ex. None adds a request, script, or font. Values below are starting points to verify against the acceptance criteria, not final.

C1 · Focus token K1 system

Design intent
Focus is unmistakable on every surface and means only “keyboard is here”.
Modification
--focus in :root; both focus rules use it. A starting point: a dark ring from the ink family (#1d2330 is 15:1 on white), 3 px with a 2 px offset, so it reads against the accent-filled buttons through the offset gap. Check the chosen value against the .msg tints.
Accessibility
Raises focus to at least 3:1; removes the hue collision with attention.
Performance
None.
Reversibility
Easy: one token.
Acceptance
As K1.

C2 · Numeric headers K2 component

Design intent
Each header sits over the edge its figures align to.
Modification
The table helpers accept {label, :num} as well as a label, and emit <th class=num …>. Add th.num{text-align:right}. The phone rules already hide thead, so there is no phone effect.
Accessibility
None (visual alignment only).
Performance
None.
Reversibility
Easy.
Acceptance
As K2.

C3 · State markers before figures K3 component

Design intent
“Below zero” marks the row without moving the number.
Modification
At html.ex lines 310 and 1348, emit <span class=below>Below zero</span> −$1,790.00 (pill first). At ≤ 40 rem, keep the .below pill on its own line at a fixed grid position (e.g. its own row in table.flow), not wherever the text wraps. Use the same radius as .badge (one pill shape).
Accessibility
Screen readers hear “Below zero, −$1,790.00”, with the state before the value. Confirm in the WI-024 walkthrough.
Performance
None.
Reversibility
Easy.
Acceptance
As K3.

C4 · Control height and select surface K4 system

Design intent
Controls in a row form one clean band.
Modification
:root{--control-h:2.5rem;--control-h-sm:2rem;--control-border:#7b8494}

7 Target craftsmanship state

  • Looks: the same quiet card stack, now on one frame. The product name, the cards, and Lock share left and right edges. Every figure in a column lines up on its right edge under a right-aligned header, and a below-zero day is marked by a pill to the figure's left, with the figure staying in line. Form rows are a single band of equal-height, white-filled controls whose labels share a baseline. One blue marks everything that can be clicked, and it never changes after a visit. Detail pages open with the thing's name as the largest text.
  • Moves: not at all. Every change is a new page that says what happened.
  • Responds: as now, a full page in well under a tenth of a second, with the result in words. A validation message sits directly under the field it concerns, with a 2 px red edge on that field.
  • Transitions: page to page, with no intermediate or settling state. The first paint is the final paint.
  • Scales: the phone keeps the four table grids. Pills sit in fixed grid positions, checkbox lists form columns, and the header's right side forms one right-aligned group.
  • Communicates hierarchy: page title, then section headings, then content, on a named scale. Solid buttons for the action a form exists for, outline for small row actions, red only for loss.
  • Expresses brand: through restraint and precision rather than ornament. The one characteristic detail stays the money typesetting: true minus, explicit plus, tabular figures, “about” figures without false cents.
  • Handles state: focus, error, attention, success, and below zero each have one colour and treatment that no other state shares.
  • Maintains consistency: through tokens in @css for colour, focus, control height, radii, and type sizes, and a recorded no-motion rule. A new page that uses the existing helpers inherits all of it.

9 Residual risks and unknowns

  • Rendering beyond one engine and font. Every observation is Chromium with DejaVu Sans. SF Pro and Segoe UI are narrower, so wrapping (“you and Mom”, “Retiring at”) will differ, and Safari draws selects differently. Smallest step: one screenshot pass in Safari on macOS and Firefox on Windows.
  • Select styling in Safari. Setting a select's background can change how WebKit draws it. Smallest step: check C4 in Safari before merging; fall back to border-only if the arrow is lost.
  • Accessibility conflict in C11. Promoting page titles to h1 changes heading navigation for screen-reader users. Keep it separate from the visual change until tested.
  • Touch targets vs page height (X1). Larger buttons help touch accuracy and cost phone height that UX-002 already flagged. This is a real tradeoff, not a defect.
  • No stated brand or visual intent. The review treats restraint as intended because it fits PRI-002 and the “nothing is scored” rule. If ACT-001 has a different intent, K11 and the subjective alternatives should be revisited.
  • Record of focus visibility. WI-024 and WI-041 record “visible focus”, from a check of presence, not contrast. K1 qualifies that note. Section 10 proposes a Defeater for a human decision.
  • Not assessed: screen-reader behaviour, 400% zoom, printing, and the export page's JSON download interaction.
